## Implementation boundaries

| Area | Implementation and invariant |
| --- | --- |
| Ledger | Migration 013 adds `admission_results`: one row per admission with owner, event, epoch, operation, canonical fingerprint and outcome. `consumed` references exactly one reservation or one direct order; `rejected` and `closed` carry code, HTTP status and message instead. `reservation_id` and `order_id` are each UNIQUE. Referenced users, events, reservations and orders cannot be deleted. A trigger rejects UPDATE; DELETE stays possible for owned cleanup. No backfill: existing reservations and orders get no row. |
| Gate placement | No global middleware and no change to `InventoryService`. `ReservationService.createReservation` and the reservation-free branch of `CheckoutService.checkout` call the common module [`admission-consumption.ts`](../src/core/services/admission-consumption.ts) on their own `PoolClient`. A checkout that carries `reservationId` takes no gate. |
| Lock order | Shared event gate → policy ensure and `FOR SHARE` → admission lock → existing checkout-key lock → existing rows. The gate and the admission lock are taken before the savepoint. |
| New reservation | Without admission fields: the existing READ COMMITTED transaction plus the gate and policy read; a protected event answers 400. With admission fields: SERIALIZABLE with the existing three attempts. The admission ID is the retry key. |
| New direct checkout | SERIALIZABLE as before. The order of the Idempotency-Key is read first, without a lock: if it exists the request is a replay and takes neither the gate nor the admission lock. Otherwise gate, policy, admission lock and the read of the submitted admission's durable result come before the checkout-key lock, and that result is judged, and the admission consumed, for the new order. The fingerprint includes the Idempotency-Key, so another key for the same admission is 409. |
| Consumption | Protected event: feature and phase checks, epoch check against the durable policy, user existence, Redis `claim` under the admission lock, `SAVEPOINT`, the existing reservation or order code, then the ledger row in the same transaction. A 4xx `AppError` from the existing code rolls back to the savepoint and commits a `rejected` row. PostgreSQL errors and 5xx roll everything back and store nothing. |
| Durable replay | The ledger row of a submitted admission is read under the admission lock before any Redis, epoch, phase or feature-flag check. For a reservation, and for a checkout once no existing order is being replayed, it is judged against the request: another owner or event answers 404, another request 409, `closed` its stored 410, `rejected` its stored error, `consumed` the current state of its target. |
| Retries | 40001/40P01 rerun the whole transaction. A `admission_results_pkey` 23505 and the policy/event FK race rerun in a fresh transaction. A refusal of a new occupation that was decided without a ledger row (feature off, recovering, epoch, unknown subject, or a claim Redis did not approve, which includes `ADMISSION_ALREADY_CONSUMED` for a result committed after the snapshot) is confirmed after its transaction ended by one ledger read on a pool connection: with no committed row the refusal is the answer, otherwise the purchase runs again and replays the row. An admission request answers 503 `ADMISSION_UNAVAILABLE` for an outage: the attempts are used up, a lock, statement or idle bound fired, PostgreSQL ended the session, or the failure did not come from the purchase work at all (no connection, or BEGIN, COMMIT or ROLLBACK failing). A defect raised by the work itself stays 500. A lock wait on the admission itself answers 409 `ADMISSION_IN_PROGRESS`. |
| Finalization | After COMMIT the route or service reports the result to Redis with the claim token. A failure is logged and never changes the response or the commit. |
| Reclaimer | The scheduler tick passes the claims `reconcile` returns to `reclaimOverdueClaims`. Per claim: shared gate, admission try-lock, ledger read in a READ COMMITTED transaction with the contract's timeouts. A committed result is reflected; with none, `closed` (`ADMISSION_EXPIRED`, 410) commits first and then the slot is returned. A held lock, a different epoch or an error leaves the slot in use. |
| Exemptions | Existing order replay and existing reservation checkout keep their checks and codes. Submitted admission fields are compared with the target's durable link only, after the existing ownership and payload checks: a different link is 409, a target without a link stays unbound whatever became of that admission. Webhook, demo settlement, queries and sweepers are untouched. |
| Feature off | `ENABLE_ADMISSION=false` never releases protection. Such an instance starts and is ready, answers 503 for a protected new occupation and serves everything that exists in PostgreSQL. |
| Guard | `assertP4AdmissionStartup` is replaced by `assertAdmissionLedger`: the product refuses to start on a database without `admission_results`. Readiness no longer depends on the absence of a protected policy. |
| Lost session | The pool hears errors of every client it creates. A session that PostgreSQL ends while a client is checked out between two queries used to emit an unheard `error`, which ends the process; now the transaction fails for its caller. This is the shared `postgres/client.ts`, together with the `retryIf` option. |
| P4 files | Three changes in `admission.service.ts`: `claim`/`complete`/`close`/`reconcile` answer 503 when the Redis control is missing instead of reading the policy on a second connection; `maintain` accepts the reclaimer; the guard replacement. No Lua, route, response schema or profile change. |

The timeouts `statement_timeout=5s`, `lock_timeout=1s` and `idle_in_transaction_session_timeout=10s` are set locally as the first statement of a purchase that submitted an admission, before the event gate, and in every reclaimer transaction. A purchase whose policy turns out to be unprotected sets them back to the session defaults and continues on the existing flow. A wait for the gate, the policy ensure or the policy row that exceeds the bound answers 503 `ADMISSION_UNAVAILABLE`.

## Findings made during the work

Each was reproduced by a test before the change that addresses it.

- **P4 `claim` cold path.** With the Redis control missing, one purchase opened two pool connections: `execute()` called `unavailableEvent()`, which starts its own transaction and takes the shared gate. Inside a purchase transaction that breaks contract §2 and can wait behind a reset's exclusive request without PostgreSQL seeing a deadlock. The internal operations now answer 503 without that lookup.
- **Lazy policy ensure and the event row.** For an event without a policy row the ensure INSERT waits on the event row through its foreign key. `event-sale-eligibility` observed that INSERT instead of the eligibility `SELECT … FOR UPDATE` as the first lock waiter. By decision D5 the test ensures the policy in its fixture; its assertions are unchanged. The first purchase of such an event still pays this wait.
- **Stale snapshot seen through Redis.** In one recorded run of the ten-way race of a single request, eight of the nine losers were told `ADMISSION_ALREADY_CONSUMED` by Redis before their snapshot could see the committed row, and one failed on the event row with 40001. All reran and replayed the same reservation. Without that rerun the losers answer 409 although their result is committed.
- **Session ended while idle in a transaction.** Found by the internal review. The purchase waits on Redis inside its transaction, and the contract's 10 s idle bound ends such a session with a FATAL. With no query active, node-postgres emits `error` on the checked-out client, which nothing heard. Ending the session with `pg_terminate_backend` during the claim reproduced two unhandled errors. The pool now hears them and the request answers 503.
- **Order replay depended on the submitted admission.** Found by the internal review. An order without a link answered 409 or 404 when its replay carried an admission that had been consumed elsewhere, because that admission's own row was judged first. The row is now judged only when a new order remains.
- **A reservation's link was visible to a stranger.** The link comparison ran before the ownership check, so a foreign reservation with a link answered differently from one without. It now runs after.
- **Admission 401 hidden by the legacy guard.** Found by the automated review of the PR. Under `ENFORCE_AUTH_USER_MATCH=true`, the production default, a purchase with admission fields and no JWT answered the legacy `UNAUTHORIZED` envelope instead of 401 `UNAUTHENTICATED` with `nextPollAfterMs`. The earlier test covered only the demo override. The admission check now runs first on both routes.
- **NUL in a tier id.** The rejection text of the unknown tier could not be stored, so the request answered 500 until its claim expired. Such a tier is now rejected before any claim.
- **A refusal decided on a stale snapshot.** Found by the external review. A request whose SERIALIZABLE snapshot predates the commit of the same request's result reads no ledger row after the lock wait. When Redis then approved the claim again, the ledger insert stopped it and a fresh transaction replayed; but when Redis refused (the instance had just lost a finalization and refuses claims until it re-verifies Redis, or the claim was past its deadline) the refusal was returned although the result was committed. Reproduced as a 503 next to a committed reservation.
- **Order replay waited for the submitted admission's lock.** Found by the external review. The earlier fix moved only the judgment behind the order replay; the gate and the admission lock were still taken first, so a replay answered 409 `ADMISSION_IN_PROGRESS` while another request held that admission's lock.
- **The first wait had no bound.** Found by the external review. The timeouts were set after the gate and the policy read, so a purchase waited behind an exclusive gate holder for as long as that transaction lived. Reproduced: no answer within three seconds.
- **CHECK and NULL.** The first form of the shape constraint accepted a rejected row without an HTTP status, because `NULL BETWEEN …` satisfies a CHECK. The constraint now requires `IS NOT NULL`.

## Purchase interface for P6

- New reservation and reservation-free checkout on a protected event send `{admissionId, admissionEpoch}` in the existing body. Both or neither; one alone or a malformed value is 400. Existing fields, the `Idempotency-Key` header and the success bodies are unchanged.
- Admission errors on purchase routes use the admission envelope `{error:{code,message},nextPollAfterMs}`. Business errors keep their envelope and code.

| Answer | When | What the client does |
| --- | --- | --- |
| 400 `ADMISSION_INVALID_INPUT` | Field error, a protected event without admission fields, or a tier id that cannot exist (over 50 characters or with a NUL) | Go to the queue; no automatic retry |
| 401 `UNAUTHENTICATED` | Admission fields without a JWT, or an unknown subject | Authenticate |
| 404 `ADMISSION_NOT_FOUND` | The admission belongs to another user or event, or does not exist | No retry |
| 409 `ADMISSION_NOT_READY` | Still waiting | Return to status polling |
| 409 `ADMISSION_REQUEST_MISMATCH` | Same admission with another command, tier, quantity, key or epoch; or fields that differ from an existing target's link | No retry with this body |
| 409 `ADMISSION_IN_PROGRESS` | The same request is still being processed, or its claim is past the deadline and not yet reclaimed | Retry the same request only |
| 410 `ADMISSION_EXPIRED` / `ADMISSION_CANCELLED` / `ADMISSION_RESET` | No new occupation possible | Check for a result first, then join again explicitly |
| 503 `ADMISSION_UNAVAILABLE` / `ADMISSION_RECOVERING` | Feature off, recovery, or a transient failure | Back off and retry the same request |
| Existing business error (for example 409 `INSUFFICIENT_INVENTORY`) | Stored as the result of this request | The same request gets it again (a direct checkout: while its key has no order); a new attempt needs a new admission |

- A direct checkout whose Idempotency-Key already has an order is answered by that order first: its replay, the existing 409 `CONFLICT` (business envelope) for a changed payload, or 409 `ADMISSION_REQUEST_MISMATCH` when the submitted admission is not the order's link. This also holds when that admission has a stored rejection for the same key.
- After an unknown outcome the client repeats the same request: same admission fields, same body, same Idempotency-Key. It gets the committed result or continues the same claim until 15 s after the first approval.
- The status API's `outcome` is filled by Redis finalization. If that failed, the entry stays `admitted`/`processing` or `reconciling` until the reclaimer finalizes it. The reclaimer first sees the claim on a tick after its deadline and has no upper time bound: while Redis or PostgreSQL is unavailable, the admission lock is held or a tick fails, the entry and its slot stay as they are and the next tick tries again. The purchase response and PostgreSQL are the authority.

## Activation and release

P5 adds no route or command (decision D8). The transition is the contract's explicit one and is what the tests perform: in one transaction take the exclusive event gate through `readAdmissionPolicy(client, eventId, 'exclusive')`, then `UPDATE admission_events SET protected = …`. An instance with the feature on converges within a tick: it initializes and publishes the namespace of a protected policy and retires that of a released one. Preconditions: every serving instance runs this version on a database with migration 013, the Redis profile is the accepted one, and at most one event is protected. A P4-version instance refuses a protected policy by its own guard; older versions are unsupported by contract §6 and cannot be fenced by application code.

### Limits kept or introduced

- The first purchase of an event without a policy row waits on the event row through the foreign key and, in the SERIALIZABLE checkout, concurrent first purchases spend one attempt on the ensure race. Activation ensures the row for a protected event.
- After a failed Redis finalization the slot stays in use at least until the claim deadline. It is returned by the first later tick whose reclamation succeeds: that needs Redis, PostgreSQL and the admission try-lock, and a tick is scheduled only after the previous one finished, so no time bound is given. Until then capacity C is reduced, as contract §5 requires.
- A reservation with admission fields runs SERIALIZABLE, so admitted buyers of one event can fail serialization on the event row and retry; three exhausted attempts answer 503. The frequency was not measured.
- A reservation on an unprotected event has no retry key, as before.
- Results are never deleted by the application, and a user, event, reservation or order that a result references cannot be deleted.
- The refusal of a new occupation costs one more ledger read on a pool connection after its transaction ended. If that read fails the request answers 503 `ADMISSION_UNAVAILABLE` instead of the refusal.
- A purchase with admission fields can answer 503 after one second behind an activation, a reset or, for an event without a policy row, the event row lock of the first ensure; before, it waited. On an unprotected event the bound applies only until the policy is read.
- A replay by Idempotency-Key reads the order without the checkout-key lock and no longer checks the event or the policy. A request whose key has an order under another event or payload gets the existing 409 `CONFLICT`, as before P5.
- After a failed Redis command an instance refuses new claims with 503 until its next scheduler tick re-verifies Redis. This is P4 behaviour; a purchase that needs a claim in that window is told to retry.
- Every new purchase share-locks one policy row and, with an admission, reads and inserts into the small ledger under SERIALIZABLE. Whether that adds serialization failures under real concurrency was not measured.
- A connection failure of the driver that carries no code still answers 500 when it is raised inside the purchase work, and always without admission fields.
- The tests that make one request wait for another's admission lock (the two snapshot cases) need that lock within PostgreSQL's 1 s `lock_timeout`. A runner that stalls for a second in that window fails them. They passed in every local run.
- No activation or release entry point exists in the product.
- The limits of P4 in [#25](https://github.com/dosacha/PeakPass/issues/25) are unchanged. None turned into a defect here.

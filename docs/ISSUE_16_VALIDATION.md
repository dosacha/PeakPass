## What the branch adds

How a scenario is judged. Every fault scenario ends with three checks. The final SQL must return no row. The transition log must be complete and without a violation: the capture reads the admission keys and subscribes in one pipeline on a raw socket, so an empty key list proves that nothing was written before the capture; commands a script runs appear in the stream as well; the capture runs until a stopped server is gone and is attached again before the new process can be reached; at the end the replayed sets are compared with what Redis holds. A capture that began late, ended by itself or ends in another state is reported as incomplete and fails the scenario. The R and C bounds are therefore checked after every recorded command, not at sampled instants. Third, the ledger of every published epoch is compared with its Redis entries.

A buyer of the fixture repeats a request with the same body, admission and key while its outcome is unknown: no answer, 429, a 5xx other than 500, or 409 `ADMISSION_IN_PROGRESS`. A 500 ends the request, so a scenario that expects another answer fails on it.

By decision D8 a defect is a broken invariant, an answer whose code differs from the contract table, a leaked 500, or a process that ends abnormally. Lower availability, a delay or a needed retry is an observation or a limit.

## Findings and observations

**F1 — one Redis restart costs two generations.** Reproduced in every run of R2 and R3 (six of six in the final rounds, and in every earlier run). When Redis is stopped while a purchase holds the event gate, a coordinator reads the failed control as missing while it still counts itself ready, and waits for the exclusive gate behind that purchase. Redis is replaced meanwhile. The coordinator then initializes and publishes the next generation under the run id it had verified before the outage. One scheduler tick later (about 260 ms in a recorded run) the coordinators verify the environment, find a control with a foreign run id, freeze it and publish a second new generation. The cause was read from `recover()` and `maintain()` in `admission.service.ts` and matches the transition log, where the `run-id` rule reports the first initialization. `FLUSHALL` (R4, R5, R6) keeps the run id and costs one generation, and so did the restarts of B2 and B8, where no purchase was in flight. Effect: an entry registered in the short-lived epoch is reset once more. Nothing was occupied twice, every answer in between was fail-closed, and no lower generation was published. It contradicts contract §6, by which a coordinator that saw the loss does not raise the generation again once the recovery is done. R2 and R3 run their final checks first, with every rule of the log except `run-id`, and then fail on one expectation: 2 generations instead of 1 and one initialization under a stale run id instead of none. Everything else in them held in each round. Not in #25. A possible change: verify the Redis environment again under the exclusive gate before the probe and the initialization.

**F2 — the exit after SIGTERM waits for a kept connection.** With a client that closes its connection the instance exited 0 after 3.3 s (K5). With a keep-alive client it exited 0 after 73.3 s (K5b), Fastify's default keep-alive timeout of 72 s: the image runs Node 18, whose `server.close()` leaves open a connection that goes idle afterwards. In B5 the browser's connection was idle when SIGTERM arrived and the instance left after 0.7 s. Everything the shutdown promises happened in order each time. An orchestrator with a shorter grace period would kill the process before that exit. A delay, so a limit by D8.

**O1 — the existing direct checkout answers 500 under contention.** A direct checkout without admission fields runs SERIALIZABLE next to reservations of the same event and answers 500 `INTERNAL_ERROR` when its three attempts run out (L1, before the activation: in the three final rounds 35 of 44, 29 of 37 and 28 of 47 such checkouts). P5 kept this answer on purpose for requests without admission fields; with admission fields the same condition is answered 503. It is the unprotected path as it was before the queue and concerns the A arm of P8.

**O2 — a reloaded page cannot reach an order whose checkout answer was lost.** The checkout key lives in the page's memory (steps 4 and 5 are as before P6). In B7 the same tab repeated the key and got the order; after a reload the page's new key was answered 409 `CONFLICT` and the pending order stayed unpaid and is left to its ten-minute deadline. No count was wrong.

**O3 — an event protected after the page loaded is shown as unprotected until a reload.** The page stops reading the queue API once it answered 404. In B6 its purchase without admission fields was refused 400, step 3 showed the error, and the queue card still said that no queue applies. Nothing was occupied.

**O4 — a PostgreSQL pool error is logged with the client object.** When PostgreSQL went away (T2, T2b), each instance logged "Unexpected PostgreSQL pool error" with the driver's client object: the connection parameters and the cancel key of the session that had just ended, and no password. Counted in the application logs of one run, four such lines per instance. Those logs are kept out of the evidence archive.

### The purchase limit

P6 asked whether the purchase limit should count replays of one identity. By decision D7 the limit stays as it is, and P7 records what it does. It counts every request on a path that contains `/reservations`, also a repeat of the same identity and `GET /reservations/:id`. In B3 one purchase took three requests and in B4 four, of the five a user has per minute; a fifth unanswered attempt would have been followed by 429. While Redis is away the limiter answers every purchase path first, 503 `RATE_LIMIT_UNAVAILABLE`, also for the checkout of an existing reservation and for a replay, and after the 5 s command bound when Redis is paused rather than stopped. The fault suites raise the limit, because their buyers repeat requests on purpose; the browser environment kept five per minute and each scenario began with empty windows.

### Not verified

- A network partition between an instance and Redis or PostgreSQL. Every fault was a process that stopped, froze or died, or lost data.
- A Redis with persistence, a replica or a failover: the product requires persistence off, and a restart always meant an empty Redis.
- A PostgreSQL outage longer than the claim deadline, a failover, and a full disk or memory limit of either store.
- More than three application instances and more than two schedulers. Clock differences between hosts: every container shared one clock.
- The purchase answers 401 and 404 in the browser; they were seen by the test process (L5) and with injected answers in P6.
- The 24 h rollover, a full queue (429 `ADMISSION_QUEUE_FULL`), the status limiter and the minimum wait of a 503: P4's and P6's evidence, not run again.
- Hidden tabs, two tabs of one user and an event change in the browser: P6's evidence, not run again. No screen reader and no other browser.
- Each browser scenario ran once, and B1–B8 ran before the later commits, which changed test code and documents only.
- The image checks ran once, before the final regression, on the same image.
- GitHub Actions, and any run of the fault suites outside this host. They need Docker and are opt-in.
- `docker-compose.flash-sale.yml`: read, not run. Its Redis service sets neither persistence off nor `noeviction` and its application service does not set `ENABLE_ADMISSION`; an instance with the feature on does not accept such a Redis.
- A review of the test code by a person or by an independent reviewer. The internal review read the code before its own fix pass; the fixes were verified by tests and by the final regression, not by a second review.
- Throughput, latency, error rates and request volume: P8.

### Limits kept or introduced

- F1, F2 and O1–O4 above.
- The fault suites take about 12 minutes for one round on this host and are not part of CI.
- Left from the internal review. Some scenarios rest on timing that a loaded host could break, in the direction of a failure and not of a false pass: K4's assertions between the claim deadline and the idle timeout, T1's upper bound of 5.9 s, M4's margins of 300 and 100 ms, K1's retry inside the dead session's sleep, K3's kill inside the 5 s command bound, R1's sequence inside the 30 s admission. M2, the second half of M3 and L4's deadline race record which side won and require neither. After a reset a second reset is looked for only during 1.5 to 2 s. The replay drops a namespace when `UNLINK` names only one of its sets, so a retirement split over several commands could be reported as incomplete; this was not seen.
- The `MONITOR` capture is for verification runs. It slows Redis down and must not run during a measurement.
- The transition log proves the bounds for the commands it recorded. Its completeness rests on the capture having begun on an empty admission keyspace and on its end state matching Redis; a restart is covered by attaching before the new process is reachable.
- `unlinked_occupation` of the final SQL reports every reservation of a currently protected event without its consumed result, also one made before the event was protected. It is meant for events protected before their first purchase, as in every scenario here.
- The stimuli (trigger, held gate, SQL users, SQL transitions) exist only in the owned test databases. The product has no activation entry point.
- The limits of P4 in #25, of P5 in #27 and of P6 in #29 are unchanged. None of the listed limits turned into a defect here; F1 is not among them.

## Successor notes

- **P8** measures product code that equals main `5016b8c`, unless F1 or F2 is changed first; a change to the reset or to the shutdown would have to be verified again by R1–R6 and K5 before a measurement.
- Budget the purchase limit: five requests per user and minute on every `/reservations` path, repeats and reads included, or set `RATE_LIMIT_MAX_REQUESTS` for all arms and record it.
- The A arm will see 500 `INTERNAL_ERROR` from direct checkouts under contention (O1), where the arms with the queue answer 503 and converge. Count them apart.
- Do not restart Redis during a measured run: with a purchase in flight it costs two generations (F1), and every registered user must join again. Stop instances with a client that closes its connections or with a grace period above 75 s (F2).
- `docker-compose.flash-sale.yml` needs the Redis settings and the feature flag named under "Not verified" before an arm with the queue can start.
- Reusable: `admission-final.sql` after every run, by `psql -f`; the replay for a separate verification run, never during a measurement; the fixture's topology as a model for several instances on one network.
- A change of the reset lifecycle, the claim deadline, the TTL, the purchase path or the limiter invalidates the evidence of the scenarios that name it.

## Commands

`npm run build`; `npx --no-install tsc --noEmit`; `npm run lint`; `npm test -- --runInBand`; `npx jest --runInBand --config jest.integration.cjs`; `npm run test:flash-sale`; `node --experimental-vm-modules load-test/payment-callback-check.mjs`. `DB_HOST/PORT/USER/PASSWORD/NAME` and `REDIS_HOST/PORT` are exported in the parent process against the owned test resources.

The fault suites: build the image (`docker build -t <tag> .`), then `ADMISSION_FAULT_IMAGE=<tag> npx jest --runInBand --config jest.integration.cjs src/tests/integration/admission-fault-redis.test.ts` (and `-process`, `-flows`). `ADMISSION_FAULT_EVIDENCE=<dir>` keeps the notes, the request list, the transition log and the application logs of a suite (the application logs can hold what O4 describes); `ADMISSION_FAULT_TASK=<label>` labels its containers. They need Docker and free loopback ports and no other resource.

The Redis-outage cases: `WAVE3_REDIS_DESTRUCTIVE=1`, `WAVE3_REDIS_CONTAINER=<name>`, `WAVE3_REDIS_CONTAINER_ID=<id>` for a Redis container that carries the label `peakpass.redis-outage=owned` and publishes 6379 on the loopback port in `REDIS_PORT`. The Docker lifecycle cases: `WAVE4_TEST_IMAGE=<tag>`.

The final SQL alone: `psql -f src/tests/integration/admission-final.sql`; no row means every check holds. The browser scenarios, the final regression script, the image checks, the sensitivity builds and the helper scripts are in the evidence archive; they are not part of the source tree and need the `agent-browser` CLI, two application containers, the proxy and a protected event.

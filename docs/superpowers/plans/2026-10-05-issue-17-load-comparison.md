# P8 same-condition A/B/C load comparison and profile calibration plan

> **For agentic workers:** Use superpowers:executing-plans inline. Main implements; any agent investigates or reviews read-only. The first session ends at Task 4 (pilot report). Tasks 5–8 start only after the user approved that report.

**Goal:** Compare A (no queue), B (queue with fixed polling) and C (the same queue with adaptive polling and jitter) under one fixed condition on one commit, calibrate R, batch and C by pilots, and hand P9 the runs, tables and wording it may quote, with the full cost of waiting next to every gain.

**Architecture:** The P2 harness is extended, not replaced. All three arms run the same image, the same Compose file and `ENABLE_ADMISSION=true`; an arm is the event's policy row (A stays unprotected, B and C are protected by the contract's explicit transition) and the generator's journey. In B and C one k6 VU is one buyer: the iteration loads the page's own `frontend/admission-polling.js` and runs one controller with injected transport, clock, timers and visibility, so the polling under test is the code P6 verified. Every run ends with the P2 SQL checks, `admission-final.sql`, and a ledger–Redis comparison; bounds on R and C are proven by one separate `MONITOR` replay run, never by samples.

**Tech Stack:** k6 1.7.1 (`constant-arrival-rate`, `http.asyncRequest`), Node (the fixture and checks must run on Node 18, CI's version), node-postgres, node-redis, Docker Compose v2, PostgreSQL 16, Redis 7. No new dependency.

**Spec:** ../../ADMISSION_CONTRACT.md (admission-v1, LF blob SHA256 `e22be4df9910811eba552f630b43170ba0cf0c8d953a54dc5a3cea34c0dcf3d1`) §4, §6–§9; ../../FLASH_SALE_BASELINE.md ("Protocol v2", "Denominators and analysis"); ../../FLASH_SALE_EVIDENCE.md; ../../ISSUE_14_VALIDATION.md, ../../ISSUE_15_VALIDATION.md and ../../ISSUE_16_VALIDATION.md (the sections #17 names); Issue #17. ## Decisions (user, 2026-10-05)

- D1 Generator: k6 stays. `constant-arrival-rate`, `preAllocatedVUs = maxVUs = buyers`, the same in every arm. The A journey code is not touched; B and C are a separate path of the same script. One iteration creates one controller of `frontend/admission-polling.js` and runs: first status read → join once the epoch is known → polling in the arm's mode → recognition → the purchase that consumes the admission (reservation for an even index, direct checkout for an odd one, both with the admission fields) → checkout, settlement and replay with A's requests and retry rules. Injected: transport (`http.asyncRequest`, timeouts from `POLICY`), clock, timers, visibility, uuid and a stand-in for `AbortController`; k6 cannot cancel a request, the timeout takes that place and the difference is recorded. The controller file is not modified. Its trace events become k6 metric points. If k6 cannot run the controller, the fallback is a synchronous loop over the same file's `successDelay` and `failureDelay` with a differential check against the controller; that switch is reported, not waited for. No Node generator.
- D2 Arms and environment: one commit, one Compose file, one image content. The Compose file changes in two places only: Redis runs `redis-server --save "" --appendonly no --maxmemory-policy noeviction`, and the application has `ENABLE_ADMISSION: "true"`. One instance, one scheduler. Limits, pool, log level and sampling as in P2 (application 1 CPU/512 MiB, PostgreSQL 1 CPU/512 MiB, Redis 0.5 CPU/256 MiB, pool 2–10, info, 250 ms). The arms differ in the policy row and in the journey with its polling mode (B fixed, C adaptive). No arm with the feature off. Fixture order: event and users by SQL → policy row ensured in every arm → B and C only: the transition of contract §6 (exclusive gate → row `FOR UPDATE` → `UPDATE protected=true`) → application start → B and C: control `mode=ready`, PostgreSQL `phase='open'`, generation and epoch equal → negative checks → load. The manifest records the application environment without secrets, three Redis `CONFIG` values, and the policy row and control before and after; the analysis requires "A stayed unprotected, B and C began and ended in one generation and epoch". The earlier A (v2.6) differs in SHA, Redis settings, VUs, drain and Docker VM: no improvement or regression is judged against it; the pilot's 10/s and 25/s values are quoted next to it for reference only.
- D3, D9 Behaviour and recognition: one tab per user, all foreground (hidden 0%), nobody leaves or cancels, a purchase follows recognition after the think time (20 ms), a user who is not admitted waits until the cutoff. Cutoff: after a per-buyer absolute deadline (arrival end + drain budget − margin) no new request starts and the outcome is recorded; an iteration interrupted at the drain cutoff makes the run invalid (P2 rule). Recognition is what the controller records; no Chrome panel is built. Reports call it "controller recognition (generator)" and the browser's recognition "not judged". The 2 s goal: per formal run, foreground `upperMs` p95 ≤ 2,000 ms over all promoted users, the unrecognized counted next to it; all three runs meeting it is "met on the generator". The hidden layer is observed in one extra run each of B and C after the formal runs (hidden 20%, assigned by index, excluded from statistics).
- D4 Load model: 1,000 buyers (the registration bound `maxWaiting` is 1,000 and is never reached), 2,000 seats (ample), quantity 2, reservation:direct 50:50, think 20 ms, checkout and settlement retry 1 after 100 ms, replay every 3, purchase limiter 1,000,000/60 s in every arm, pool 10, sampling 250 ms. The warmup cohort is the first 250 buyers. The horizon (arrival end + drain budget) is the same in every arm and cohorts follow the scheduled arrival time. Arrival condition, fixed in advance: A pilots at 10/s×40 s (400 buyers, warmup 10 s) → 25/s×40 s (warmup 10 s) → 50/s×20 s (warmup 5 s), one run each. The formal condition is the lowest step at which A misses the P2 stability criteria; if at that step both the unfinished share of the measurement cohort and the write failure share are below 5%, one step higher. Without any overload the highest step is used and described as "a condition in which A is not overloaded". Formal: one condition × A/B/C × 3 = 9 runs in the order A-B-C / B-C-A / C-A-B.
- D5, D6 Calibration (the order of the pilots, the rule C = 3R and the selection rules are superseded by the decisions of 2026-10-06 below; the rest stands): only R, batch and C. TTL 30 s, claim 15 s, lease 120 s, tick 250 ms, polling and limiter stay. Candidates are commits of the local branch `claude/issue-17-p8-pilot`, never pushed or merged: cut from the work branch, one commit that derives the polling boundary as `5 * admissionProfile.rate`, and one commit of constants per candidate. A measurement always runs from a clean tree; each candidate's diff against the work branch and its hash go into the run evidence. A harness fix is made on the work branch and the pilot branch is rebuilt. No contract revision before the pilots. R pilot (arm B, formal arrival condition, one run per candidate): candidates min(highest arrival rate at which A was stable, 20) and half of it rounded up; batch = ⌈R/4⌉, C = 3R, the rest seed. C is 3R instead of the seed 8 so that C does not bind first and hide the effect of R (the user's approved reading). Chosen: the largest R whose run is valid and meets "write failure share after admission ≤ 1%, paid p99 after admission ≤ 2,000 ms, final SQL 0 rows"; if neither does, half once more, one run. C pilot (R fixed): C ∈ {8, ⌈1.5·R·h⌉, 3R} with h the mean slot occupation in seconds (admittedAt → purchase response) of the chosen R run; 3R reuses that run, equal values are skipped. Chosen: the smallest C whose promotion achievement during the backlog (while somebody waits) is ≥ 95% and that keeps the criteria. A foreground expiry is analysed and reported; the TTL is not changed. Confirmation: one C-arm run with the chosen profile, and one `MONITOR` verification run (arm B, the capture attached before activation and application start, replayed with `admission-transition-log`, zero violations, excluded from statistics).
- D7, D10, D11 are proposed with numbers in the Task 4 report and approved there. Direction: D7 profile numbers and the revision name (the contract stays `admission-v1`, only the profile revision changes), contract §7, §9 and §11, the change gate of #9, and the re-verification scope (build, lint, unit, integration, harness, image checks, one round of the fault suites, the `MONITOR` run; the browser scenarios are not repeated because the frontend, the TTL and the limiter do not change, with that reason recorded). D10 stability and stop criteria (proposal: completion ≥ 99%, write failure ≤ 1%, paid p99 after admission ≤ 2,000 ms, for B and C promotion achievement ≥ 90%; the whole wait is published as a cost without a threshold and judged as "completed inside the horizon"; the 2 s recognition goal is judged apart). D11 where raw evidence lives (formal run ZIPs committed, pilot and invalid runs kept locally with hash and size in the index; settled after sizes are measured).
- D8 Retries and limits: A as in P2 (a reservation is never repeated, an unknown result is `unknown_outcome`). The request of B and C that consumes the admission follows the controller (the same identity repeated automatically up to four times while undecided); first attempts and repeats are separated, giving a first-attempt failure share and the outcome after repeats. A 401, 403 or 429 on a purchase path, an admission 429 or `ADMISSION_QUEUE_FULL` makes the run invalid.
- D12 One read-only independent review before the formal runs (Task 6).
- D13 The pre-merge wording of `docs/ISSUE_16_VALIDATION.md` (the three places of #32 §5) is corrected, facts only, in the P8 document commit (Task 7).

Metrics and denominators (approved with the design): completion = unique HTTP paid whose order and ticket identity match the final SQL / the whole scheduled measurement cohort. Outcomes: paid, not joined, still waiting, admission expired, admitted without purchase, business refusal, unknown, `http_xxx`, and a cancellation if one happens; none leaves the denominator. Throughput = unique paid (HTTP = SQL) inside a window / its length, for the arrival window and for the whole horizon. Purchase write error share = non-replay purchase attempts (reservation, checkout, settlement) answered 429, 5xx or not at all; polling and join are not in it; A's 500 `INTERNAL_ERROR` and the 503 of B and C are separate columns and 409 is counted by code. Whole wait = arrival → paid p50/p95/p99 (conditional on paid, the unfinished counted). After admission = recognition → paid (A: arrival → paid) and admittedAt → purchase response. Polling = status requests in total, per registered user, per-second maximum and p95, by reason (timer against outside the cadence). Recognition = lower and upper p50/p95 by layer over all promoted. Queue = waiting, active, claims and window sampled every 250 ms (the same commands run in A), and every `admittedAt` checked against R per rolling second. Three repeats are a median with [min–max]; percentiles are never pooled.

Validity (approved with the design; the bound for pool samples of v3 runs and the start gate are changed by the decisions of 2026-10-06 below): invalid = the P2 list (dropped, started ≠ offered, arrival lag > 250 ms, script exception, malformed success, missing observation or evidence, generator not observed, host pressure, failed cleanup, dirty tree) plus a change of policy, epoch or generation, a Redis restart (run id), a Redis setting that differs, an admission 429 or `ADMISSION_QUEUE_FULL`, an iteration interrupted at the cutoff, a missing trace. Integrity = the P2 SQL checks, any row of `admission-final.sql`, a ledger–Redis mismatch, HTTP paid that SQL does not have: the series stops, the raw run is kept, nothing is re-analysed with the survivors only, and it is reported before product code changes. A Redis restart or reset is invalid: keep the raw run and repeat the slot once under a new id with the suffix `r`. A stretch in which a late reclamation reduced C is product behaviour and valid, published with its interval and count. A slow application exit is outside the window; its duration and exit code are recorded (F2). End of a run: k6 ends → wait until active and claims are 0 (bound and actual time recorded) → Redis dump → application stop → SQL snapshot → `admission-final.sql` (0 rows) → ledger–Redis comparison → cleanup (`admission_results` first). Start gate: the P2 rule (≥ 2 GiB free memory, 3 samples 5 s apart, at most 10 attempts 30 s apart) applied and recorded by the run script, host CPU sampled with it; a CPU bound is proposed in Task 4 from the idle distribution of the pilots. `MONITOR` is never attached to a measured run, and no build, test or review runs on the host during one.

## Review focus

- A queue arm that is not really protected, or an A arm that is: each run records the policy row and the control before and after, and B and C send one purchase without admission fields that must be refused before the load.
- Polling mixed into the purchase error denominator, or waiting buyers dropped from the completion denominator: the analysis filters purchase stages by name and counts every scheduled buyer's outcome.
- A generator that polls differently from the page: the check drives the real controller file through the script and compares every planned delay with contract §7 computed independently; each run reports planned against actual delay.
- A buyer cut off silently: the cutoff ends a journey with an outcome and without a new request; an iteration k6 interrupts makes the run invalid.
- A bound claimed from samples: the 250 ms samples describe the queue; R per rolling second is checked on every `admittedAt` of the Redis dump and both bounds on the replay of the verification run only.

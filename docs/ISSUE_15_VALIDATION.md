One controller serves one context (API base, user, event) and is disposed before the next one starts, so an answer of an earlier context has nowhere to land. A request for a demo session gives up after the 5 s request timeout, and the next request starts a new one. |

## Choices the contract text does not fix

Recorded as P6 behaviour, without a contract revision (decision D11 and rulings in the plan's ledger). A change to any of them changes what P8 measures.

- A return to the tab does not shorten the wait a failure asks for (its backoff and a server minimum): no request is sent before that wait ends, and a return inside it sends the retry at its end.
- The hidden interval has no jitter. A poll that fails in a hidden tab is retried no sooner than 15 s while the tab stays hidden; that interval is not part of the failure's wait and does not hold back the request on return.
- 5xx other than 503, timeouts and a 200 that cannot be used take the 503 backoff.
- Polling pauses while a purchase is open; a purchase is not held back by a backoff of the status API.
- A purchase request times out after 10 s; automatic repeats: four.
- Requests outside the timer cadence: the first read of a page (`recover`), the one read on return (`return`), and one read right after a purchase result, a refused join or a refused cancel (`refresh`), also in a hidden tab. In fixed mode two status requests can therefore be closer than 1 s; they never overlap. A state that stopped polling on 401 or another 4xx is read once on every return.
- The recognition marker is keyed by epoch and admission, not by run. An admission id is unique, so this is at most one sample per run, epoch and admission; a sample belongs to the run of the page that recorded it. A key with the run was tried and withdrawn: the page of the next run then recorded an admission that had been recognized as missed.
- When several layer conditions hold, `reconnect` wins over `hidden`; the raw flags are recorded next to the label.
- A finished entry is not polled (the server sends no interval for it). A join made in another tab is seen on return to the tab, on "check again" or when a join answers 409.
- Reset and a change of the event do not cancel the server-side entry.

## Findings made during the work

- **`Retry-After` is not readable by a cross-origin page.** The server sends it on 429 only and CORS exposes no header. The page uses the body's `nextPollAfterMs`, from which the server derives that header (decision D8, no backend change). In the 429 run the trace recorded the body's wait and no header. The 503 answers of the admission service and its Lua carry `nextPollAfterMs: 1000` (read in the code, seen in S6).
- **The clamp makes the jitter one-sided at both bounds.** With base 1000 the planned delays were 1000–1192 ms and with base 5000 they were 4779–5000 ms. This is what the contract formula yields; P8 should expect it.
- **Chrome repeats a POST once by itself** when a reused connection closes without an answer. With one answer lost, the browser's own repeat returned the same reservation and the page saw a single request. The proxy therefore loses two answers to reach the page's own retry. A lost answer can so cost two requests of the purchase limit: with five page attempts, three of which Chrome repeated, the application saw eight `POST /reservations`, five answered 201 with the same reservation and three answered 429.
- **A wait asked for by the server can outlive the admission.** In one run a 429 asked for 21347 ms while the entry was admitted; the page kept the wait and the entry had expired when it read again. A purchase stays possible during such a wait.
- **Hidden timers run late.** Two hidden polls planned at 15000 ms were sent after 15316 and 15997 ms, and a hidden status request without an answer was given up after 5989 ms instead of 5000 ms, as the contract expects from browser throttling.
- **Step 3 after a reload.** An entry recovered as admitted could not be used because the page had not read the events. The page now reads them on load.
- **A controller of the previous user.** After a change of the API base one render created a controller for the new base with the previous user; its request was aborted before any answer was applied. The queue user is now bound to the API base and mode its session was issued for, and a session answered after a reset is dropped.
- **Keyboard and screen-reader output.** Opening or closing the cancel confirmation moved the focus to `body`, and both live regions kept the text of an earlier state. One button now opens and closes the confirmation, and both texts follow the state.
- **A failure in a hidden tab held back the return** (internal review). The wait of a poll that failed while hidden was 15 s, and that wait blocked the one request on return and the join and cancel buttons, up to half of a 30 s admission. Reproduced by two failing tests; the wait is now what the failure asks for (S15).
- **Step 3 stuck as running** (internal review). When the event was changed during a purchase without an answer, step 3 stayed "running" and its button stayed disabled on the other event until Reset; an unconfirmed purchase showed "running" without end. Reproduced in the real browser; the step is released with its controller and an unconfirmed purchase has its own label (S16, S17).
- **A request log line that was not the request** (internal review). For a status poll without an answer the page's request log repeated the stored answer of the previous poll. Reproduced in the real browser with a request that is accepted and never answered; the line is now written from the poll itself (S14).
- **Quantity after a recovered purchase** (external review). A purchase of quantity 1 whose answers were lost, repeated after a reload, set the reservation but left the form at its default 2, so step 4 sent 2 and the checkout answered 409. Reproduced in the real browser (S18); the form now follows the reservation.
- **A join key outliving its attempt** (external review). After a join whose answer was lost, the page read the entry the join had created but kept the key; after a cancel, "join again" sent the old key and the server replayed the cancelled entry. Reproduced in the real browser (S19) and by two failing tests; the key now ends once the server shows another entry than the one its attempt started from.
- **A late reservation read** (external review). The read behind "load reservation" was not tied to its context: answered after the event had changed, it put the first event's reservation, tier and quantity on the second. Reproduced in the real browser with the answer held back at the proxy (S20); such an answer is now dropped.
- **An earlier reservation read on the same event** (external review, second round). The context check of the reservation read compared only the controller: a read for an earlier admission that answered after a new join and purchase on the same event put the older reservation, tier and quantity back on the page, and step 4 would have checked out the older reservation. Reproduced in the real browser (S21); the read now also has to belong to the admission the page shows.
- **A demo session request without an answer** (external review, second round). Every request of the page waits for one shared session request, which had no time limit. After a 401 made the page ask for a new session that was never answered, no status request was sent again, also after the server answered again: in the real browser (S22) nothing reached the server for 150 s and the waiting entry expired after its 120 s lease while the card still showed it waiting. The session request now gives up after 5 s and the next request asks again.
- **A reservation read answered after Reset** (auto-review). Reset clears the page's flow but keeps the queue context, so a read that was out passed the context check and restored the reservation and the done state of step 3. Reproduced in the real browser (S23); Reset ends the session generation, and the read now checks it.
- **A 401 attempt that was not on record** (auto-review). A queue request answered 401 is repeated once with a new demo session of the same user; the trace and the request log showed only the repeat, so two requests looked like one. Reproduced in the real browser (S24); the rejected attempt is now an `auth-retry` record in the trace and a line in the request log.
- **The recognition marker across tabs** (auto-review). `localStorage` has no cross-tab transaction: two tabs that apply the same admission at almost the same moment can both record it, and concurrent writes of the marker list can lose one. Not changed in code; the analysis keeps the earliest record per run, epoch and admission across all exported traces (see "Trace for P8").
- **A stored purchase on another API base** (auto-review, second round). The tab's record of a purchase without an outcome was keyed by user and event only, so a controller for another API base whose server holds the same ids (for example a second deployment of the same seed) restored it as unconfirmed and offered to repeat it there. Reproduced by a failing test; in the browser the stored key had no base. The key now names the API base, the user and the event.
- **A purchase retry answered after Reset** (auto-review, second round). Reset kept the queue controller, so a retry of a purchase whose answer was lost was still sent after Reset, and its answer put the reservation and the done state of step 3 back on the cleared page. Reproduced in the real browser (S25). Reset now stops a purchase that is still being sent: an attempt still out is dropped, no repeat follows, and the request waits as unconfirmed for its button, while the queue keeps its schedule. A first fix (`0b1c3b5`) replaced the controller on Reset instead; in S23 the new controller read the state at once, also for an entry whose polling had ended, and inside a wait the server asked for (A15) that read would have been a request too many.
- **A newer reservation of another tab** (auto-review, second round). "Load reservation" was offered only when the page held no reservation. After a second tab of the same user joined again and bought, the first tab's card showed the newer reservation as the outcome while the page kept the older one, and nothing could load the newer. Reproduced in the real browser (S26). The button now appears whenever the page holds another reservation than the card's outcome.
- **A trailing slash in the stored purchase's API base** (auto-review, third round). The key of the second round took the API base as typed, but the transport removes trailing slashes, so `http://host/` and `http://host` reach one server and had two keys: after the user changed only the slash, the unconfirmed purchase and its button were gone until the old spelling was back. Reproduced by a failing test only; no browser run. The key now removes trailing slashes as the transport does.
- **A rejected token on "load reservation"** (auto-review, fourth round). The read returned on a 401 and kept the session, and a consumed admission is not polled, so nothing replaced a token the server rejects while its `expiresAt` was still ahead: every click sent the same token until Reset. Reproduced in the real browser (S27): with the token of the first read rejected at the proxy, two clicks ended in two 401 and no reservation. The read now replaces the session once on a 401, only with a session of the same user, and repeats; the rejected attempt stays in the request log. After the change S27 shows 401, a new session and 200 on the first click, and S23 (Reset during a held read) holds.
- **The accessibility audit lists at most ten nodes of a rule, and audits a button under the pointer in its hover colour.** A first reading ("nothing inside the card") was wrong for the first reason, and one audit missed the join button for the second. The audits below print the node count of each rule and move the pointer away first.
- **The static server sends no cache policy.** The browser once served a file edited seconds before from its cache; that check was repeated, and the helper that opens the page now reads every frontend file with cache `reload` first.
- **Request lists with headers.** The browser tool's JSON request list and a raw HAR contain the `Authorization` header. The checks use the plain list, a reduced HAR and the application's request log, which record no header. Before that was noticed one demo token of the owned environment (ten minutes lifetime, signed with a random local secret) was printed to the operator's console. It is in no file of the repository or of the archive.

## Trace for P8

Events, each with `t` (local monotonic ms) and `wall`:

- `poll`: `seq`, `reason` (`recover`, `timer`, `retry`, `return`, `refresh`), `mode`, `hidden`, `tSend`, `tRecv`, `status`, `code`, `timedOut`, `state`, `phase`, `position`, `serverTime`, `nextPollAfterMs`, `serverMinMs` and `retryAfterMs` (what the server asked for with a failure), `plannedDelayMs`, `actualDelayMs`, `baseMs`, `u` (the jitter draw), `changed`. The interval effect and the jitter effect are separable: `baseMs` is the server base, `u` the draw and `plannedDelayMs` the result.
- `poll-aborted`: a status request an action pre-empted. It may have reached the server.
- `join`, `cancel`, `purchase` (one per attempt), `visibility`, `mode`, `epoch`.
- `auth-retry`: a queue request answered 401, with its method, path, times and code. The page repeats it once with a new demo session of the same user, and that repeat is the request recorded under its own type. The demo session request itself is not in the trace.
- `recognition`: once per epoch and admission, when this browser first applies the entry as admitted. `serverDeltaMs` is `serverTime − admittedAt`, both from Redis `TIME`, so no local wall clock is involved. The delay lies between `lowerMs = serverDeltaMs + (tApply − tRecv)` and `upperMs = serverDeltaMs + (tApply − tSend)`. `layer` is `foreground`, `hidden` or `reconnect`; `visibleAtPromotion`, `hiddenBetween`, `hiddenAtApply`, `failuresBefore` and `viaRecover` are the raw flags. `reconnect` means that the answer was the first of a page, followed a failed request, or that the promotion is older than the page's visibility log; it does not mean that the promotion happened while disconnected.
- `recognition-missed`: an entry that ended before this browser applied it as admitted, with its final state. The entries that expired unrecognized are the events with state `expired`; an entry first seen as consumed or cancelled is recorded too.

A page's trace lives in memory, while the marker survives a reload. Read `snapshot()` before the page is reloaded or closed: a recognition whose trace was not read is lost and is not recorded again. The marker keeps one browser profile from recording an admission twice in the usual cases, but it is not a cross-tab transaction: when a user has several tabs, keep the earliest `recognition` per run, epoch and admission across all exported traces and drop the others.

### Limits kept or introduced

- The colour contrast of the existing palette (above).
- In live mode with a selected event the page now sends `POST /demo/session` and reads the events on load, without a click. It needs both to recover a waiting user.
- The pending purchase template is per tab (`sessionStorage`), keyed by API base, user and event, and Reset keeps it. Another tab learns the outcome from the status API only. "Load reservation" does not close a restored unconfirmed purchase; repeating the same request does.
- Loading a newer reservation replaces the reservation, tier and quantity on the page and keeps an order or settlement already there, as a new reservation made in the same tab does.
- The markers keep the last 50 admissions of a browser profile; an older admission seen again would be counted again. A recognition is lost when its page is reloaded before the trace was read (see "Trace for P8").
- An event change keeps a reservation that is already on the page, as before P6; Reset clears it. Only a late reservation read is dropped.
- A demo session request that is not answered within 5 s is given up and asked again with the next request; each attempt counts against the server's limit for demo sessions.
- The demo has one fixed user per application process. "Another user" was a second process, reached by changing the API base.
- A cross-origin page sends a preflight for each request once the browser's short preflight cache has run out: 13 preflights next to 37 status requests in S1. They reach the application and are not counted by the admission limits.
- The limits of P4 in [#25](https://github.com/dosacha/PeakPass/issues/25) and of P5 in [#27](https://github.com/dosacha/PeakPass/issues/27) are unchanged. None turned into a defect here. S6 uses the behaviour of #25 item 1 (an instance with the feature off answers 503 for an existing control) as its stimulus, and S9 and F2 saw the 30 s TTL elapse in real time through the API; the claim deadline stays P7's.
